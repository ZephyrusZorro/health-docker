# Architecture Overview

Nishat HMS is split into two independently deployable tiers:

| Tier | Tech | Responsibility |
|------|------|----------------|
| `backend/` | Laravel 12, PostgreSQL 16, Redis 7, Sanctum, Reverb | Domain logic, persistence, authorization, realtime broadcast |
| `frontend/` | Next.js 15 (App Router), React 19, TanStack Query, Tailwind 4 | Staff-facing SPA + public marketing site + booking wizard |

The backend is the source of truth. The frontend consumes a single versioned REST API under `/api/v1/*` and authenticates via Sanctum personal access tokens.

## Domain packages

The Laravel app is organised by **bounded context** rather than by Laravel file type. Each context owns its own migrations, models, services, events, controllers, and form requests.

```
app/
├── Models/
│   ├── Identity/       — facilities, departments, users, providers, patients
│   ├── Scheduling/     — schedules, slots, appointments, queue tokens
│   ├── Clinical/       — encounters, observations, conditions, prescriptions
│   ├── Admission/      — wards, rooms, beds, admissions, discharge summaries
│   ├── Pharmacy/       — medications, batches, dispenses, purchase orders
│   ├── Laboratory/     — lab tests, orders, samples, results
│   ├── Billing/        — charge catalog, invoices, payments, refunds
│   └── Audit/          — audit logs, notifications, system events
└── Services/
    ├── Identity/UhidGenerator
    ├── Scheduling/SlotGenerator, TokenGenerator
    ├── Pharmacy/FefoDispenser
    ├── Billing/InvoiceAggregator
    └── Notifications/NotificationDispatcher
```

### Why this layout?

Each subdirectory mirrors a single responsibility from the SRS. Moving a feature means moving one folder, not grep'ing across ten directories. New developers can reason about *Billing* without needing to know anything about *Laboratory*.

## The data model

The schema is roughly FHIR R4-shaped. We did not adopt FHIR as a storage format (too verbose for OLTP), but the models translate 1:1 into FHIR resources at the API boundary. Specifically:

| Local model | FHIR resource |
|-------------|---------------|
| Patient | Patient |
| Provider | Practitioner + PractitionerRole |
| Encounter | Encounter |
| Observation | Observation |
| Condition | Condition |
| Allergy | AllergyIntolerance |
| Prescription + PrescriptionItem | MedicationRequest |
| LabOrder + LabOrderTest | ServiceRequest |
| LabResult | Observation (lab category) |

All clinical codes default to **LOINC** (observations/labs) and **SNOMED CT** (conditions/diagnoses). Where these are unavailable, the `code_system` column identifies the fallback (e.g., local facility codes).

## Non-negotiable invariants

Three rules are enforced at the database and service layer, not merely in controllers:

1. **UHID is permanent.** `patients.uhid` is unique, indexed, and generated by `UhidGenerator` inside a row-locked transaction per-facility. Merges never reuse UHIDs.
2. **Invoices are polymorphically sourced.** Every `invoice_items` row has `source_type` and `source_id` that reference the originating clinical event (encounter, dispense, lab order, bed charge). You can always audit which clinical action produced which charge.
3. **FEFO dispensing is enforced, not recommended.** `FefoDispenser::dispense()` will refuse to dispense from any expired batch and always consumes the earliest-expiry non-expired batch first. It runs inside a transaction with `lockForUpdate()` to prevent over-dispensing.

## Authorization model

Authorization is **role-based** via Spatie Permission, but every controller checks **permissions**, never roles. Roles are a UX convenience for admins; permissions are the actual authorization primitive.

Ten roles ship by default (super_admin, hospital_admin, doctor, nurse, receptionist, pharmacist, lab_tech, cashier, management, patient). ~60 permissions across 10 categories. The mapping lives in `database/seeders/RoleAndPermissionSeeder.php` and is authoritative — running that seeder resets roles to the system baseline.

`super_admin` bypasses all gates via `Gate::before()` in `AuthServiceProvider`. Every other role must have the explicit permission.

## Realtime

Three events broadcast over Laravel Reverb (WebSocket):

- `QueueUpdated` — channel `facility.{id}.queue` — for waiting-room displays
- `BedAssigned` — channel `facility.{id}.beds` — for the ward occupancy board
- `LabResultReady` — private channel `patient.{id}.results` — for the ordering doctor

The Next.js frontend uses `laravel-echo` + `pusher-js` to subscribe. No polling.

## Background work

Two queues:

- `default` — email, SMS, WhatsApp dispatch; audit writes; non-critical jobs
- `critical` — invoice recalc after clinical events; stock ledger updates

Five scheduled commands (see `routes/console.php`):

| Schedule | Command | Purpose |
|----------|---------|---------|
| Daily 02:00 | `hms:generate-slots` | Materialise 14 days of appointment slots |
| Every 10 min | `hms:send-appointment-reminders` | 60-min-before reminders |
| Daily 07:00 | `hms:pharmacy-alerts` | Low-stock + expiring-batch digest |
| Every 15 min | `hms:bed-cleanup-check` | Flags beds stuck in cleaning |
| Daily 03:15 | `hms:audit-rotate` | Archives logs past retention |

## Audit

Every state-changing API call writes to `audit_logs` via the `AuditLogMiddleware` + `LogsActivity` trait. Retention defaults to **2555 days (7 years)**. Older logs archive to JSONL on object storage, then are deleted from the hot table by `hms:audit-rotate`.

Audit records are **append-only**. There is no UPDATE or DELETE permission on `audit_logs` at the application layer; the table is write-once except by the rotator (which has explicit DB-level privileges in production).
